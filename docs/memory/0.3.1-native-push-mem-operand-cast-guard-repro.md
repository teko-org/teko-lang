## Root cause PINNED (gdb, ASLR-off, deterministic) — NOT a large/corrupt displacement

The panic is the checked `to u32` cast on `push_mem_operand_x86`'s disp8 write
(`(disp & X86_BYTE_MASK) to u32`, `encode_x86_64.tks:522`). Disassembly of the panic path in gen2:

```
5868f: mov  $0xff,%rax          ; X86_BYTE_MASK
58696: lea  0x40(%rsp),%r10
5869b: mov  (%r10),%r10         ; disp (i64) loaded 64-bit
5869e: mov  %r10d,%r14d         ; r14d = LOW 32 of disp        <- narrow-tracked
586a1: and  %eax,%r14d          ; r14d = disp & 0xff  (32-bit AND): [0,255]
586ab: cmp  $0,%r14d ; jge      ; floor  value >= 0  (ok)
58716: movabs $0xffffffff,%rax  ; ceil = 4294967295 (CAST_CEIL_U32), 64-bit in rax
58720: cmp  %eax,%r14d          ; 32-BIT compare  (bug)
58723: jle  ok                  ; value <=(SIGNED32) 0xffffffff(=-1): false for any v>=0
58729: jmp  panic
```

gdb at `+0x507` (the `cmp`): `r14 = 0x8` (value = a NORMAL 8-byte frame-slot displacement),
`rax = 0xffffffff`. The value is small, non-negative, valid; the disp8 SELECTION is correct. The
panic is a SPURIOUS `to u32` overflow trap: the ceiling `value <= 4294967295` is emitted as a 32-bit
SIGNED compare where `0xffffffff` reads as `-1`, so `8 <= -1` fails and traps.

Why 32-bit: `disp = mem.offset to i64` (`push_mem_operand_x86:513`). `mem.offset` is `i32`
(`minst.tks:32`, `MMem.offset`), loaded narrow (`select_load_x86`, `wide=false`, zero-extended).
`i32 to i64` is a lossless widen, so `lower_cast_fit_guard` (`lower.tks:814`,
`cast_is_lossless_widen`) returns unchanged and `lower_int_cast` reuses the operand VReg — with NO
width-tracking update. The x86 isel keys operation width off `vinfo[vreg].wide` (`select_bin_x86`
reads `a_info.wide`), so `disp` stays `wide=false`; the `& mask` and the `to u32` guard's ceiling
compare are all selected 32-bit. A 32-bit compare against `CAST_CEIL_U32` (a value outside signed-32)
is unsound.

The C route never runs `push_mem_operand_x86` (it emits C, `codegen.tks`'s `emit_cast`), so this
native-only encoder path is exercised for the FIRST time by gen2 — the bug had never fired.

Family: native isel/lowering integer-WIDTH tracking (a widening `iN to i64` cast drops the wide bit),
NOT the region-lifetime family and NOT a displacement-width selection error.

## The fix (`src/lir/lower.tks` only — native lowering; C route byte-identical)

A narrow-to-64-bit integer widen must materialize a wide-TRACKED value instead of eliding to the
narrow operand VReg. `lower_int_cast` now re-tracks a `to i64`/`to u64` widen from a <64-bit source
(`cast_widens_to_64`) through `lower_widen_to_64`: `0 | value` — a `IOr` whose FIRST operand is a
`LConstInt` (always selected 64-bit), so the isel selects the OR at 64-bit and records the result
`wide=true`. The value is bit-identical to what the register already holds (every 32-bit x86 op —
`mov`/`movzx` load, `select_param_x86`'s 32-bit arg `mov`, an `and` — clears the upper half, so a
narrow value is ALREADY zero-extended in its 64-bit register; `0 | v == v`). Only the width
TRACKING advances, so downstream ops (`& mask`, the
`to u32` guard's ceiling compare) select the 64-bit form and the guard is sound. No new MInst / isel
/ regalloc surface, no `arm64` change, no `ZExt`/`SExt` semantics change. `codegen.tks` (the C route)
is untouched, so its fixpoint is byte-identical.

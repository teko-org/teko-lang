# Item 13 — `monomorph`-stage memory leak: root-cause investigation

DEEP INVESTIGATION ONLY. No fix, no surface decision. Read-only on product code.
Method: static reading + reasoning, plus the owner-authorized diagnostic evidence
already on record. **`teko test` was NOT run in any form during this
investigation** (see §7). This document states a root-cause HYPOTHESIS with the
code path, the evidence chain, the relation to the native-OOM docs, why no safe
minimal repro was constructible, and candidate fix DIRECTIONS for the owner +
architect to decide later.

---

## 0. TL;DR

The `monomorph` OOM on the test-inclusive path is **not an infinite loop and not
an unbounded generic-instantiation explosion** — those are both bounded (the
PHASE-2 fixpoint has a 5000-stamp ceiling that returns an *error*, not an OOM, and
the diagnostic did **not** hit it). It is a **super-linear peak-RSS blow-up of the
`monomorphize` pass itself**, whose every allocation lands in the **never-rewound
root region**, driven up by the larger, generic-denser test-inclusive corpus until
it crosses the container/`ulimit` memory ceiling.

Two structural amplifiers inside `src/checker/monomorph.tks`, both still open per
the roadmap's own flattening plan:

1. **No region-per-phase boundary (AL5, open).** `monomorphize` runs entirely in
   the task ROOT region. It CLONES AST per instantiation (PHASE-1 clones every
   non-generic body incl. every `.tkt` test body; PHASE-2 stamps each generic
   instance's body; `stamp_all_instance_methods` clones every method of every
   generic-type instance). None of it is wrapped in `region_new/enter/leave`, so
   every clone + every transient list accumulates and is freed only at
   program/test teardown. Peak RSS = Σ(all clones + all scratch) with no reclaim
   seam mid-pass.

2. **Linear-scan multiplicative structure (achatamento target #2, open).**
   `stamp_all_instance_methods` is O(instances × methods × items): for each method
   of each generic-type instance it calls `find_template_method(items, …)` — a
   full linear scan of the whole program's items — and there is **no ceiling** on
   this loop (unlike PHASE 2). The dedup ledgers (`mono_seen`, `mono_inst_seen`)
   are also linear scans, and the PHASE-2 `queue` is concatenated with **no dedup
   at enqueue** (`mono_inst_concat` just pushes). On the test corpus (many
   collection/generic instantiations at many concrete types, `assert`/test helpers
   invoked at thousands of sites) both `instances` and `items` are much larger than
   a source-only build, so the multiplicative work — and the cloned-body volume it
   parks in root — grows super-linearly.

The **"monomorph 0 instances"** in the diagnostic is a **static placeholder**
printed by `phase_begin` *before* `monomorphize` is even called
(`src/build/project.tks:353`); it is **not** an internal progress marker and does
**not** localize the crash to the "start / before the first instance". The correct
reading is only: *the OOM happened somewhere inside `monomorphize`, which never
returned.* This corrects the framing in the task brief — the "0" clue cannot be
used to place the blow-up in a setup sub-phase.

## 1. Architecture recap (what actually runs)

- `gen0` is built from `bootstrap/teko.c`, which is the **generated C transpilation
  of the `.tks` sources** (not a hand-written twin). So the monomorph algorithm
  that runs inside `gen0` **is** `src/checker/monomorph.tks`. Reading the `.tks` is
  reading the code that OOMs. (`table_generic_instances`, `monomorphize`,
  `stamp_all_instance_methods` all appear verbatim in `bootstrap/teko.c`, e.g.
  `bootstrap/teko.c:105164`, `:97313`.)
- The front-end driver is `src/build/project.tks`. The monomorph phase is:
  ```
  project.tks:353  var mono_phase = phase_begin("monomorph", count_only_text(0, "instances"), mode)
  project.tks:354  var checked = match checker::monomorphize(pre.prog, pre.table) { … }
  project.tks:361  var instances = if checked.items.len > pre.prog.items.len { … } else { 0 }
  project.tks:362  phase_end_ok(mono_phase, count_unit_text(instances, instances, "instances"))
  ```
  There is **no `phase_tick` between 353 and 362** — the real instance count is
  only known *after* `monomorphize` returns. Hence the `0` is a hardcoded start
  placeholder (confirmed against `src/build/progress.tks:191`, which notes the
  monomorph fixpoint "size only settles once the phase ends").

## 2. What is bounded (ruled out as the cause)

- **PHASE-2 fixpoint (`monomorphize`, `monomorph.tks:1420-1453`).** The queue is
  drained; each dequeued instance not already in `stamped` is stamped ONCE (its
  body is not re-cloned — `if mono_inst_seen(stamped, inst) { continue }`,
  `:1424`). A `ceiling = 5000` (`:1417`) on `stamped.len` returns
  `error { message = "monomorphization exceeded the instantiation ceiling (5000) …" }`
  (`:1425-1427`). The diagnostic OOM'd **without** reporting that error, so
  **unique free-fn/method instantiation did NOT exceed 5000** — polymorphic-
  recursion explosion is **ruled out** as the direct cause.
- **Non-termination.** Every loop in the pass is index-bounded over a finite
  collection; PHASE 2's growth is bounded by the 5000 ceiling. No infinite loop.
- **The general copy-grow O(n²) list bug.** Already CURED: `teko::list::push`
  lowers to `tk_slice_push`, whose live-tail witness cache was moved from a
  16-slot linear cache to a **65536-bucket pointer-keyed hash**
  (`src/runtime/teko_rt.c:4297-4321`), taking a source-only self-build from
  ~98 GB/98 M allocs back to O(n). The `monomorph` OOM is **not** the generic
  push-O(n²); it survives that cure. (Residual push cost is discussed in §4c as a
  secondary amplifier, not the root cause.)

## 3. Where the memory actually goes (the accumulation sites)

All of the following allocate into the **task ROOT region** — a bump arena over a
chunk list that is **not rewound during the pass** (freed only at program end or
per-`#test` rewind; see `teko-mem-model-empirical.md`: "single region for whole
process doesn't isolate lifetimes … leak-to-root S2 discipline").

### 3a. PHASE 1 — clone every non-generic body (incl. every test body)
`monomorphize`, `monomorph.tks:1384-1409`. For every non-droppable `TFunction` it
runs `mono_block(f.body, empty_s, …)` (`:1390`) and pushes a freshly rebuilt
`TFunction` into `kept` (`:1391-1392`). `mono_block` (`:997-1011`) rebuilds every
statement via `mono_tstmt` (`:1005-1006`) — **fresh AST nodes**. On the
test-inclusive program this clones **all `.tkt` test-function bodies too**, which
the `--no-verify` source-only build discards (`filter_tkt`). That extra cloned
volume is exactly the "test-path-only" delta and is pure root-region residence.

### 3b. `stamp_all_instance_methods` — unbounded, O(instances × items)
`monomorph.tks:1321-1335` → `stamp_instance_methods` (`:1281-1307`). Structure:
```
for inst in table_generic_instances(table):            // NO ceiling
    for method in mono_decl_methods(inst):
        find_template_method(items, stem, method.name)  // LINEAR SCAN of all items
        stamp_one_instance_method(…)                    // clones the method body
        fns  = push(fns, …)
        insts = mono_inst_concat(insts, …)
```
Two costs compound: (i) `find_template_method(items, …)` is a full linear scan of
the whole program per method (the achatamento plan's target #2 — "busca direta,
não varredura"), so *time* is O(instances × methods × items); (ii) each stamped
method is a **cloned body** parked in root, so *memory* is
O(instances × methods × avg-body). Crucially this loop has **no 5000-style
ceiling** — it is bounded only by the actual generic-type-instance count, which
the test corpus inflates (collections/generics exercised at many concrete `T`,
`K`/`V`).

### 3c. Transient lists with no reclaim seam
- `mono_inst_concat` (`:219-228`) grows the `queue`/`acc`/`insts` MonoInst lists via
  plain `teko::list::push` (**not** the free-old `push_fo`), and each `MonoInst`
  carries a `Subst` (three parallel lists). The PHASE-2 `queue` is concatenated
  with **no dedup at enqueue** (`:1393`, `:1399`, `:1413`, `:1444`), so it can hold
  many duplicate instances (dedup happens only at *dequeue* vs `stamped`).
- `subst_typeexpr` / `subst_typeexpr_args` / `type_to_texpr` (`:242-323`) allocate
  fresh `TypeExpr` trees per substituted annotation, all in root.
- `mono_block`'s statement chain `out` DOES use `teko::mem::push_fo` (`:1006`,
  free-old on grow), so that one chain is well-behaved — evidence that the leak is
  the *aggregate un-scoped residence*, not a single mis-written buffer.

## 4. Why the test-inclusive path OOMs but a normal `--no-verify --release` build does not

Same `monomorphize`, same root-region model — the only variable is the **input
program**:

- **Size.** `--no-verify` drops the `.tkt` corpus (`filter_tkt`); `test .` compiles
  the test parser + every `*_test.tkt` (the checker phase reported **9593 items**
  on the diagnostic run). PHASE-1 clones every one of those extra bodies (§3a).
- **Generic density.** Test files instantiate collections/generics at many concrete
  types and call generic `assert`/test helpers at thousands of sites, inflating
  both `table_generic_instances(table)` (drives §3b's uncapped loop) and the number
  of discovered `MonoInst` (drives §3c's queue).
- **No reclaim to absorb it.** Because nothing in `monomorphize` is region-scoped
  (§3), the source-only build **already peaks ~3.4 GB** for the whole build
  (owner-verified, exit 0). The test-inclusive program's larger + denser input adds
  a super-linear increment on top of an already-3.4 GB baseline, crossing the
  3 GB `ulimit`/container ceiling → `deliberate panic: out of memory` inside
  `monomorphize`.

This is consistent with a **scale × super-linear-in-root-region** failure, and
inconsistent with a runaway loop (which would ignore corpus size and would trip the
5000 ceiling as an *error*).

## 5. Relation to the native-OOM / flattening docs — DISTINCT leak, SAME structural family

- **`docs/design/native-lowering-oom-por-funcao-0.3.1.md`** — a **DISTINCT** leak.
  It is the **native** route: `lower_program` (`src/lir/lower.tks:13732`) builds the
  whole `LModule` in the root region before the fused per-function encode; a
  different pass, different file, native backend. Item 13 is the **C route**,
  `monomorph.tks`, a front-end pass that runs *before* codegen/lowering. The native
  doc's Tier-1 fused-encode cure does not touch monomorph.
- **`docs/memory/achatamento-de-n2-plano-0.3.1.md`** — names the two mechanisms
  behind item 13 but does **not** cure them: **target #2** "scoped hash maps (busca
  direta, não varredura)" = the `find_template_method`/`mono_*_seen` linear scans in
  §3b; **AL5** "region-per-phase" = the missing reclaim seam in §3. Both are listed
  **open/novo** there.
- **`docs/memory/teko-mem-model-empirical.md`** — states the shared *root model*:
  "single region for whole process doesn't isolate lifetimes … leak-to-root S2
  discipline." The AL1/AL3 push-O(n²) cure (65536-bucket hash) that fixed the native
  self-host OOM is **orthogonal** and already landed; item 13 survives it.

**Conclusion:** item 13 is a **distinct instance** of the same structural disease
(everything on the root region + linear-scan checker hot spots), at a **new site
(`monomorphize`) on the C route**, not addressed by the native-OOM Tier-1 cure nor
by the push-cache hash.

## 6. Safe minimal repro — NOT safely constructible (with reason)

No safe minimal repro was constructed, on purpose:

- **A small synthetic input will not OOM.** Normal `--no-verify --release` builds —
  including small generic programs — pass through this exact `monomorphize` without
  OOM (owner-verified). The failure is emergent at corpus scale; a toy input cannot
  reproduce it.
- **Any input large/dense enough to actually OOM monomorph necessarily approaches
  the very memory ceiling whose exhaustion crashed the container.** Provoking it is
  precisely the forbidden outcome under the task's non-negotiable safety rule.
- **The specific trigger is the test-inclusive assembly**, which only the `teko
  test` path builds (`filter_tkt` keeps `.tkt` only under `test`). Reproducing the
  exact trigger is the one command the safety rule forbids.

Therefore the deliverable stops at the static hypothesis, as the task explicitly
permits.

### 6a. SAFE measurement DESIGN for a later, isolated run (do NOT run here)
For the owner to confirm super-linearity in a **disposable VM** (never this
container, never `teko test`): generate a family of synthetic `.tks` programs that
declare one generic type with a method and instantiate it at N distinct concrete
types (N = 50, 100, 200, 400 …), each built with
`TEKO_BACKEND=c <compiler> <dir> -o <freshdir> --no-verify --release` under
`ulimit -v` and `timeout`, capturing the `report_phase_rss("monomorph")` line
(`project.tks:363`). A super-linear RSS-vs-N curve confirms §3b/§3c; a flat/linear
curve refutes it and redirects to §3a corpus size. This exercises the suspected
path through a NORMAL build only — no `.tkt`, no test runner — but is still
memory-provoking, so it belongs in an isolated environment, not here.

## 8. Candidate fix DIRECTIONS (NOT a fix — for owner + architect to decide later)

Directions only, ordered by expected leverage; each must preserve the `gen2==gen3`
fixpoint and pass all Laws:

1. **Region-per-phase for `monomorphize` (AL5).** Wrap the pass so its transient
   clones/scratch live in a child region that is dropped after the kept-items are
   copied out to root — mirroring the native fused-lowering `region_new/enter/leave`
   discipline (`project.tks:3701-3704`). Highest leverage: turns Σ(all scratch)
   into O(one item's scratch) resident at a time. Requires care that `kept`/the
   returned `TProgram` are copied to root before the child drops (spine/escape).
2. **De-linearize the instance-method stamp (achatamento #2).** Replace
   `find_template_method(items, …)` (linear scan per method, `monomorph.tks:1291`)
   and the `mono_seen`/`mono_inst_seen` scans with a hash index keyed by
   `(stem, method-name)` / mangled name, built once. Cuts §3b from
   O(instances × methods × items) to O(instances × methods).
3. **Dedup the PHASE-2 queue at ENQUEUE.** Have `mono_inst_concat` (or the enqueue
   sites) drop instances already in `stamped`/already queued, so the `queue` and its
   carried `Subst`s stop accumulating duplicates (`monomorph.tks:219-228`,
   `:1393/1399/1413/1444`). Bounds §3c residence and the drain's scan count.
4. **A ceiling / metric on `stamp_all_instance_methods`.** It currently has none
   (§3b). Even without a fix, adding a fail-loud ceiling + `report_phase_rss`
   sub-tick would convert a silent OOM into a diagnosable honest stop and localize
   future regressions (M.1 fail-loud spirit).
5. **Free-old on the MonoInst accumulators.** Where a MonoInst list is a proven
   linear chain, use `teko::mem::push_fo` (as `mono_block`'s `out` already does,
   `:1006`) instead of plain `push`, so superseded buffers are parked for reuse.

Sequencing note (bootstrap seed): any such change is `.tks`-only (Teko-only law);
`bootstrap/teko.c` is frozen output and must not be hand-edited — the cure lands via
a normal reseed once implemented, and must not use a language feature absent from
the current seed.

# 0.3.1.0 — the first stop of the native self-build is `byte`, not aggregates

**Lane**: `remodel/0.3.1.0-linux-native`, based on upstream `38a8875` (the org's `.31` tip).
**Goal of the lane** (owner's platform-sequenced plan): the Linux leg generates NATIVE. Version
formula unchanged, bump stays incremental; macOS/Windows/wasm keep the C route; C lives until
0.3.1.4. Done = the fixpoint holds in native on the Linux leg.

## Why Linux is sequenced first — breadth, not ease (owner's ruling, 2026-07-28)

This is **not** because Linux is easier. The four Linux legs (`x86_64-glibc`, `x86_64-musl`,
`arm64-glibc`, `arm64-musl`) measure the **same shared lowering** (`src/lir/lower.tks`) across four
platform combinations — the greatest breadth per unit of effort.

**What is shared and what is not:** the LIR lowering is shared across all platforms. Only byte
emission is per-platform — instruction selection (`isel x86-64`, `isel arm64`, `isel wasm`), object
writers (ELF, PE, Mach-O), and platform-specific variants like `B1-fp` (floats on x86-64) and
`B1-args` (stack arguments on Windows). **Therefore degraus 1 through 6 already benefit macOS,
Windows, and wasm**, untouched: the `byte` machine class, variant cases by keyword, short-circuit
`&&`/`||`, aggregate push, fat `match`, and the variant wrapper — all are fixes in shared code that
any platform reaching here will receive.

**What remains for the other platforms — and it can be substantial:** macOS and Windows have their
own emission work. The owner said it plainly: *"they can have a lot of things that won't work"*.
That work is the entire emission half: instruction selection for x86-64 (including `B1-fp` for
floats), `B1-args` (Windows stack passing), the PE `TimeDateStamp` (which broke Windows fixpoint
in 0.3.0.31), and the object writers. All orthogonal to the shared lowering.

## The measuring loop — 66 seconds, no network

```sh
sh scripts/build_gen1_from_c.sh bootstrap/teko.c src .gen1   # 26s — the trampoline
TEKO_BACKEND=native ./.gen1/teko . -o .gen2-native --no-verify --release   # 40s — to the stop
```

## What it says today

```
teko: .: native backend N1: a push whose element is an AGGREGATE
(`struct`/`class`/variant/optional/closure) needs slice elements held BY VALUE — this backend's
aggregate value is the address of a per-INSTRUCTION frame slot, so a push in a loop would store
the same address every iteration (N2)  [in `teko::backend::emit_u32_le`]
```

## Why that message is misdiagnosing

`emit_u32_le` pushes **bytes** into a `[]byte`. Nothing about it is an aggregate. Reduced to
twelve lines and narrowed by element type:

| element | verdict |
|---|---|
| `i32` | compiles |
| `u8` | compiles |
| **`byte`** | **the "AGGREGATE" stop** |
| `f64` | a different, already-named stop: `isel x86-64: B1-fp` (the float family) |

The cause is in the type model, and it is two missing match arms, not a redesign:

`src/checker/type.tks:126`
```teko
pub type Type = variant Prim | Byte | Char | Str | Slice | Optional | Named | Variant | Func | Error | Void | Ptr | Uptr | Reference | Null
```

`byte` is its **own variant member**, a sibling of `Prim` — `PrimKind` (`type.tks:11`) has no
`Byte` (`typer.tks:1792` records the intent as "byte AS u8"). Two functions in `src/lir/lower.tks`
enumerate `Prim` and fall through on everything else:

- `is_register_value_type` (`lower.tks:5325`) — `Prim => true`, enum-`Named => true`, `_ => false`.
  A `byte` lands in `_`, so the push guard calls it an aggregate and raises the stop above.
- `ltype_of` (`lower.tks:270`) — `Prim`, `Void`, `Named`, then `_ => LType::Ptr`. A `byte` is
  therefore given the **address-shaped, 8-byte** machine class instead of a one-octet integer.

The second is the more serious of the two: it is not a guard, it is the machine class every
downstream consumer reads. A `[]byte` element stride, an index load, and a push `sizeof` would all
agree on 8 where the truth is 1.

## What this changes about the lane

The stop pointed at "aggregate value semantics in the native backend" — a keystone redesign
(deep copy for aggregate fields, a layout-sized stride the array-literal store and index load must
adopt). That work is real and still ahead, but it is **not** what blocks the self-build today.
The first degrau of 0.3.1.0 is narrower and nameable: **`byte` has no machine class in the native
backend's LIR mapping.**

## Next steps, in order

1. Give `Byte` its arm in `ltype_of` (a one-octet integer class) and in `is_register_value_type`
   (`true`). Check `Char` for the same gap while there.
2. Confirm the three stride consumers agree on 1 for `[]byte`: the array-literal store, the index
   load, and the push `sizeof` argument. A guard that stops honestly is better than three
   consumers that disagree silently.
3. Re-run the measuring loop. Expect a NEW stop — `f64` already shows `B1-fp` waiting behind this
   one. Each stop is a degrau; record it here rather than widening the fix to meet it.

## Degrau 3 — `&&` and `||` have no lowering at all

```
teko: .: native backend N1: integer operator not yet lowered (N2)  [in `teko::backend::needs_lr_save`]
```

The named function is two lines: `func_any_call(f) && func_any_ret(f)`. The operator that stops is
`&&`.

### The minimal probe — 10ms instead of 3 minutes

`src/probe.tks`, with the virtual `src/main.tks` being just `exit(probe())`:

```teko
pub fn probe(): i32 {
    let a = true
    let b = false
    if a && b { return 1 }
    0
}
```

`TEKO_BACKEND=native <gen1b>/teko . -o out --no-verify --release` reproduces the message verbatim,
with `[in `probe::probe`]`.

### The cause

`src/lir/lower.tks:829` — `lower_expr` sends EVERY `TBinary` to `lower_binary`, which lowers both
operands eagerly and then asks `lbinop_of` for an opcode. `lbinop_of` (`lower.tks:411`) splits on
the RESULT's `PrimKind`: float family, else integer family. `&&`/`||` are typed `Bool`
(`checker/typer.tks:745`, `type_logical_binop`), `Bool` is not a float kind, so a LOGICAL operator
is routed into `lbinop_int` (`lower.tks:441`) and dies in its `_ =>` at `lower.tks:453`.

Same shape as degrau 1 and 2 — a `_ =>` swallowing a case the rest of the compiler understands —
but the fix is NOT a new arm in that match. `&&`/`||` must SHORT-CIRCUIT: `lbinop_int` returning
`IAnd`/`IOr` would evaluate the right operand unconditionally and miscompile every
`p != null && p.field` guard in the compiler's own source. The lowering is control flow, and the
LIR already has every piece it needs — `lower_coalesce` (`lower.tks:3793`) is the exact template:
branch, two arms, a merge block whose single block-arg is the value.

### Why the message misleads

It says "integer operator". `&&` is neither integer nor an arithmetic operator; it is named that
only because `bool` rides in the integer family of `lbinop_of`'s two-way split. It also says "not
yet lowered", which reads as a missing OPCODE, when what is missing is a control-flow shape.

### Degrau 3 — CLOSED

`lower_binary` (`src/lir/lower.tks`) now intercepts `&&`/`||` BEFORE lowering either operand and
sends them to `lower_logical`, built in `lower_coalesce`'s shape: branch on the left operand into
either a `rhs` block (which lowers the right operand) or a `short` block (which materializes the
deciding constant — 0 for `&&`, 1 for `||`), both jumping to a merge block whose single block-arg
IS the expression's value.

The right operand must NOT be lowered eagerly, which is why the interception sits above
`lower_binary`'s body and not inside `lbinop_int`'s match: returning `IAnd`/`IOr` there would have
been the one-line "missing arm" fix and it would have MISCOMPILED every `p != null && p.field`
guard in the compiler's own source. This degrau is where the "a missing arm behind a `_ =>`"
pattern of degrau 1 and 2 stops holding: the arm was missing, but the arm was not the fix.

Regression: `short_circuit_and_or`, a member of the `own_native` corpus channel
(`examples/regressions/own_native/`) — the full truth table plus two rows whose RIGHT operand is a
divide-by-zero, so an eager lowering traps instead of merely returning a wrong number. Corpus exit
42 on both the native and the C route. Root `teko test .`: 1026 unit tests ok, regression summary
byte-identical to the pre-fix compiler's.

## Degrau 4 — aggregate slice elements. AN ARCHITECTURE DECISION, NOT A DEGRAU. STOP HERE.

```
teko: .: native backend N1: a push whose element is an AGGREGATE (`struct`/`class`/variant/optional/
closure) needs slice elements held BY VALUE — this backend's aggregate value is the address of a
per-INSTRUCTION frame slot, so a push in a loop would store the same address every iteration (N2)
[in `teko::backend::wrap_plain_words`]
```

`wrap_plain_words` (`src/backend/encode_arm64.tks:1633`) is `acc = teko::list::push(acc,
plain_word(ws[i]))` inside a loop — `EncWord` is a struct. This is the SAME message the lane's
first measurement reported, but this time it is not misdiagnosing: degrau 1 removed the `byte`
false positive that was wearing it, and what is left underneath is the real thing.

### What was measured before stopping

The stop's own text says slice elements must be held BY VALUE, which reads as "the array-literal
store and the index load must be widened too". They do NOT need to be, and that changes the shape
of the decision. This probe PASSES natively today:

```teko
pub type Point = struct { x: i32; y: i32 }

pub fn probe(): i32 {
    let ps = [Point { x = 1; y = 2 }, Point { x = 3; y = 4 }]
    if ps[0].x != 1 { return 1 }
    if ps[1].x != 3 { return 2 }
    if ps[1].y != 4 { return 3 }
    0
}
```

It passes because `[]Aggregate` is, today, a slice of ADDRESSES: `ltype_of` gives a struct
`LType::Ptr`, so `lower_array_lit` (`lower.tks:6285`) uses stride 8 and stores the element's
address, and `lower_index_slice` (`lower.tks:6271`) loads one 8-byte word back — an address, which
IS the aggregate's value in this backend. The model is SELF-CONSISTENT, and its three consumers
already agree on 8.

The single place it breaks is the one that stops: an `alloca` is one frame slot per INSTRUCTION,
not per EXECUTION, so `loop { out = push(out, T { … }) }` pushes the same address N times.

### The decision, stated as two options

1. **By-value elements.** `[]Aggregate` gets a layout-sized stride: the array-literal store
   memcpies, the index computes `base + i*size` and does NOT load, the push passes the item's
   address with `esz` = layout size. Every consumer changes together, including the ones not yet
   written (slice-of-slice, a `for x in xs` binding, an `xs[i] = …` store, an aggregate argument).
2. **Fresh storage per push.** Keep `[]Aggregate` as a slice of addresses — every consumer above
   stays untouched and the probe keeps passing — and make `push` copy the aggregate into a FRESH
   runtime allocation, storing THAT address. It fixes exactly the aliasing that stops, and it also
   fixes the value-semantics hole the address model has anyway (`let p = …; xs = push(xs, p);
   p.x = 9` currently mutates the pushed element). Its cost is an ownership/lifetime call on the
   allocation (arena/region), which is a runtime decision, not a lowering one.

Option 2 is much narrower and option 1 is what the stop's text presumes. Choosing between them is
an architecture call with a runtime-lifetime consequence, so this cargo STOPS here rather than
picking one alone. It is on the critical path and it is unavoidable: the compiler is written in
slices of structs (`[]EncWord`, `[]LInst`, `[]MInst`, `[]LFunc`, …), so nothing else in the native
self-build can be measured until it is decided.

### Degrau 4 — CLOSED for `struct`/`class`, by the owner's OPTION 2 (ruling 2026-07-28)

The owner ruled: **narrow option now, by-value model later, as its own lane.**

- The slice of ADDRESSES STAYS. No consumer changed — the array-literal store still writes with
  stride 8, the index load still reads one word back, and the two-`Point` literal probe above still
  passes natively.
- A push whose element is an aggregate now COPIES the aggregate into a FRESH per-EXECUTION
  allocation and pushes THAT address.
- The value-semantics hole in ASSIGNMENT (`let a = ps[0]` aliases instead of copying) is left OPEN
  ON PURPOSE. It is the next lane, not this degrau.

What landed (`src/lir/lower.tks`, `src/runtime/teko_rt.{c,h}`):

| piece | what it does |
|---|---|
| `push_box_bytes` | 0 for a register value; the element's registered layout size for a nominal aggregate; the honest stop otherwise |
| `box_push_item` | emits `tk_slice_elem_box(&item, size)` and pushes the RETURNED address |
| `tk_slice_elem_box` (runtime) | `tk_alloc(esz)` + `memcpy` — the copy is bump-allocated in the ROOT arena |

**Ownership/lifetime — the hard half.** Teko has automatic arena memory and no GC, so the question
was not "how to copy" but "who owns the copy". The answer is the one the push itself already uses:
`tk_slice_push` grows the buffer that will HOLD the address through `tk_alloc`, i.e. in the root
region. Boxing the element in the SAME region makes the element's lifetime equal to the lifetime of
every buffer that can name it — one `tk_arena_pop`/`tk_regions_free_all` reclaims both, and no
element can outlive or predecease its holder. There is no new lifetime rule to teach anyone.

**Why the runtime was touched.** The LIR has no memcpy op and no allocation op, and inventing an
unrolled load/store copy in the lowering would have put an ALLOCATION POLICY (which region? which
alignment?) into codegen, where the arena is invisible. One 4-line runtime entry keeps the policy
where the arena lives. It is the smallest possible addition and it is documented at both sites.

### The stop that SURVIVES, narrowed

`unsized_aggregate_push_stop` still fires — for an aggregate whose byte width the ELEMENT TYPE
ALONE does not fix:

- an **optional** (`T | null`) and a **variant**: their tag+payload wrapper is allocated to the
  ACTIVE case's payload width (`lower_null_union_construct`/`lower_variant_construct` size it per
  CONSTRUCTION), so a copy sized from the static type would over-read a narrow construction;
- a **closure**: its value is one address whose captured environment is a SECOND allocation a flat
  copy would alias rather than clone;
- a **nominal with no registered layout** (an interface).

A guard that stops honestly is better than one that passes in silence. Closing the variant/optional
arm means making the wrapper's size a whole-TYPE fact, which is a separate decision with its own
consumers — it is NOT pulled in here. (DEGRAU 6 made it one: the VARIANT arm is closed at
`variant_wrapper_bytes()`. The optional and the closure arms survive.)

### THE DIVERGENCE THIS INSTITUTIONALIZES — `NATIVE-AGG-SLICE-BY-ADDRESS`

Search for that token: it is in `lower_list_push`'s doc, in `push_box_bytes`'s doc, in
`tk_slice_elem_box`'s two runtime comments, and in the corpus `.tkr`'s Feature block.

**The native backend's `[]Aggregate` is a slice of ADDRESSES; the C route's is a slice of VALUES.**
Both give the same answer for construction, indexing, field reads and — now — for a push. They
DIVERGE on assignment out of a slice:

```teko
mut a = ps[0]
a.x = 99          // C route: `ps[0].x` stays; native: `ps[0].x` becomes 99 (a is an ALIAS)
```

That divergence is DELIBERATE and time-boxed: it is what makes degrau 4 a narrow change instead of
a keystone redesign. It must be watched until the by-value-element lane closes it. Nothing in the
regression corpus may claim either side of it — a scenario that pinned the aliasing behaviour would
make the divergence permanent by accident.

### The regression, designed to fail without the fix

`examples/regressions/own_native/` (the degrau-3 corpus channel), three members:

- `push_aggregate_in_loop` — four `BoxPt { x = i; y = i * 10 }` pushed ONE PER ITERATION, then every
  element checked against its own iteration's values plus an explicit `ps[0] != ps[3]` distinctness
  check. With the naive stand-in (push the `alloca` address as-is) every element reads back as the
  last one and the program exits 23; before degrau 4 it did not compile at all.
- `push_aggregate_copies_the_item` — mutating the source binding AFTER the push must not reach the
  element. This is the second hole the box closes, and the naive stand-in fails it too.
- `push_class_in_loop` — the `class` arm, boxed by the same registered layout width.

Both routes exit 42 (`TEKO_BACKEND=native` and `TEKO_BACKEND=c`), from ONE program.

## Degrau 5 — a `match`-VALUE is not a fat-pointer producer. CLOSED.

```
teko: .: native backend N1: fat-pointer receiver `match-expression` not yet lowered (N2)
[in `teko::backend::encode_one`]
```

Reached the moment degrau 4 cleared the aggregate push. Reproduced in 10ms:

```teko
pub fn probe(): i32 {
    let n: i32 = 2
    let s = match n { 1 => "one"; _ => "three" }
    if s.len != 5 { return 1 }
    0
}
```

A MISSING ARM with the template already in the file — the degrau-1/2 shape, not the degrau-3 trap.
`lower_fat_expr` accepts a closed producer set (literal, array literal, bound local, struct field,
`if`-expression, direct call) and a match-value was not in it. `lower_match_fat` is
`lower_match_value`'s arm chain wearing `lower_if_fat`'s two-param merge: the subject lowers once,
each arm's tail goes through `lower_block_value_fat`, and the merge's FIRST two block-args are the
(ptr, len) pair with the reassigned scalars after it. The dead fall-through past the last arm test
carries a defensive pair whose halves each take `lfallback_const` of their OWN machine class (a bare
`0` for the length would wasm-encode i32-narrow and collide with the real edges).

`native_match_fat_known_stop` went red the day the gap closed, exactly as its own note asked. Its
positive claim was promoted into the `own_native` corpus (`fat_match_value`). The project itself
could NOT be promoted: one stop deeper its `speak_or` hits
`fat-pointer interface-dispatch result not yet lowered` — a different family (the call ABI, not the
producer set) — so it was renamed `native_iface_fat_known_stop` and pins THAT stop by name.

## Degrau 6 — a variant whose member is FAT. An architecture decision — RULED ON, and CLOSED.

```
teko: .: native backend N1: slice match pattern not yet lowered (N2) [in `teko::backend::encode_one`]
```

The named site is `match emit_epilogue(layout) { []u32 as w => w; error as e => return e }` — the
spelling the compiler's own source is written in, hundreds of times over.

### Reproduced in 10ms, and the C route compiles the same program

```teko
fn make(n: i32): []i32 | error {
    if n == 0 { return error { message = "no" } }
    let xs: []i32 = [1, 2, 3]
    return xs
}

pub fn probe(): i32 {
    let r = make(1)
    match r {
        []i32 as xs => { if xs.len != 3 { return 1 } }
        error => { return 2 }
    }
    0
}
```

### Why it is NOT the missing arm it looks like

`lower_bind_pattern_test` refuses `bp.is_slice` in one line, which reads like degrau 1 and 2. It is
not. Measure the CONSTRUCTION side and the gap is upstream of the pattern:

- `lower_variant_construct` allocates the uniform wrapper `{ i32 tag; payload }` of
  `8 + ltype_size(pty)` bytes and `store_variant_payload` stores ONE word of class `pty` at offset 8.
  For a `str`/`[]T` member `ltype_of` answers `Ptr`, so **the LENGTH is dropped at construction** —
  the probe's `make` lowers today and already builds a lossy wrapper.
- `bind_payload_at8` binds ONE scalar VReg through `ctx_bind`, not `lenv_bind_fat`.

So giving `is_slice` its arm would bind an `xs` whose `.len` reads whatever sits past the pointer.
That is degrau 3's trap wearing degrau 1's clothes: the arm is missing, and the arm is not the fix.

### The decision this needed


**What is a variant/optional wrapper's SHAPE when a member is fat?** The candidate is a uniform
`{ i32 tag; ptr; len }` (24 bytes, 8-aligned) that every member pays for, which changes together:
the construction store, the payload bind (scalar vs fat), the return path, the `Optional` twin, and
every existing tag test's offsets.

It is not separable from degrau 4's open half, and that is the strongest reason to decide them
together: `unsized_aggregate_push_stop` still refuses to box an optional/variant element precisely
because the wrapper is sized PER CONSTRUCTION rather than per type. A uniform wrapper closes that
stop as a side effect; a per-construction one keeps it open forever.

It is on the critical path — the compiler's own error handling is written in `T | error` unions with
fat `T`s — and nothing further in the native self-build can be measured until it is decided.

### Degrau 6 — CLOSED by the owner's ruling of 2026-07-28: a UNIFORM 24-byte wrapper

**`{ i32 tag@0; ptr@8; len@16 }`, 8-aligned, for EVERY variant/optional and EVERY case.**

One shape, one set of offsets, no special cases. The owner chose it knowing it wastes 8 bytes on
every case that has no fat member, and knowing the compiler is full of them: in a compiler that is
cheap, and uniformity is the opposite of what has bitten this lane four times — always one case
falling into a `_ =>`.

**Rejected explicitly, so they are not re-proposed:**

- *Box the fat payload behind one word.* It would deepen the by-address aggregate model that is
  already marked for demolition (`NATIVE-AGG-SLICE-BY-ADDRESS`).
- *Size the wrapper per member.* A variable payload offset is exactly the extra surface on which a
  case can fall through a `_ =>` again.

**Accepted cost:** 8 bytes per variant value with no fat member.

### The consumers that had to move — the list that keeps the next one from forgetting

The wrapper is written in ONE place and read in FOUR, and the width is asked for in THREE more.
Every one of them is named here because a forgotten consumer is a silent miscompilation:

| consumer | file | what changed |
|---|---|---|
| `variant_wrapper_bytes` / `variant_payload_offset` / `variant_payload_len_offset` / `variant_wrapper_align` | `src/lir/lower.tks` | NEW. The shape is now four named facts instead of arithmetic spread over two constructors |
| `lower_variant_construct` | `src/lir/lower.tks` | allocates the uniform width/alignment; passes the payload's TYPE (not its `LType`) down |
| `lower_null_union_construct` | `src/lir/lower.tks` | same, for the null-bearing twin |
| `store_variant_payload` | `src/lir/lower.tks` | splits on `is_fat_type` into `store_fat_variant_payload` (ptr@8 + len@16, through `lower_fat_expr`) and `store_scalar_variant_payload` (one word @8) |
| `bind_case_payload` (was `bind_payload_at8`) | `src/lir/lower.tks` | splits the same way: `bind_fat_case_payload` loads BOTH halves and `ctx_bind_fat`s them; `bind_scalar_case_payload` keeps the single-word load |
| `bind_null_union_payload` | `src/lir/lower.tks` | passes the payload TYPE through instead of collapsing it to an `LType` |

### Degrau 7 — string equality. A MISSING ARM, and CLOSED (same cargo, own commit)

```
teko: .: native backend N1: `str` has no single PrimKind, asked by the comparison chain (N2)
[in `teko::backend::name_in_symbols`]
```

Reached the moment degrau 6 cleared the slice pattern. The named site is
`syms[i].name == name` — a `str == str`. Reproduced in 10ms with three literals.

`lower_compare` sends every operand through `prim_kind_of`, which answers "which SINGLE machine
kind is this?". A `str` is two words and has none, so the chain stopped. `lower_str_compare` now
intercepts a `str`-typed subject BEFORE the chain and calls the runtime's own `tk_str_eq` with the
two ABI-flattened pairs `(a.ptr, a.len, b.ptr, b.len)` — the same flattening every fat argument
already gets, and the same by-symbol runtime use `tk_slice_push`/`tk_alloc` are. **No runtime entry
was added**; `tk_str_eq` has always been there.

TWO details that are the whole difference between an answer and a coin flip:

1. **The C `bool` return only defines its LOW BYTE.** `tk_str_eq`'s body is `memcmp(...) == 0`, so
   the bits above that byte carry the comparison's leftovers. The first build tested the whole
   register against zero and reported `"abc" == "abd"` as TRUE. The result is now narrowed through
   `narrow_extern_return`'s 8-bit unsigned shape first — the very hole
   `extern_return_narrow_of_prim` documents and leaves open for declared externs.
2. `!=` is the same call with the opposite predicate (`str_eq_predicate`), and an ORDERED `str`
   comparison (`<`, `>=`, …) keeps its own named honest stop — it would need `tk_str_cmp` and a
   lexicographic contract this backend has never claimed.

Regression: `str_equality`, a member of the `own_native` corpus — same-length-but-different, a
last-byte-only difference, two equal strings in DIFFERENT buffers (a pointer comparison would call
them different), and the empty pair (whose pointer is null). 42 on the native route and on the C
route.

### Degrau 8 — the next stop, reached in 22s, AND a silent miscompilation found beside it

```
teko: .: native backend N1: a push whose element is the nominal type `teko::backend::MInst`,
which has no registered layout … [in `teko::backend::push_minst_block`]
```

`MInst` is a DECLARED variant (`pub type MInst = variant MAlu | MAluImm | …`), so it reaches
`push_box_bytes` as a `checker::Named`, not as the inline `checker::Variant` degrau 6 closed. Whether
that is one more arm (look the name up in the variant table and answer `variant_wrapper_bytes()`) or
an architecture call depends on a question NOT yet answered: **is a declared-variant value the same
24-byte wrapper an inline union's value is?** Do not assume it — measure it, because the probe below
says something is already wrong there.

**MEASURED AND NOT FIXED HERE, CLOSED IN ITS OWN CARGO (`cargo/0.3.1.0-match-arm`, see the section
after this degrau):** a `match` over a DECLARED variant picks the WRONG ARM natively, silently.

```teko
type Circle = struct { r: i64 }
type Square = struct { s: i64 }
type Shape = variant Circle | Square

fn pick(n: i64): Shape { if n == 0 { return Circle { r = 7 } }; Square { s = 9 } }

pub fn probe(): i32 {
    match pick(1) { Circle => { return 3 }; Square as s => { if s.s != 9 { return 4 } } }
    0
}
```

Native exits **3** (the `Square` value took the `Circle` arm); the C route exits 0. It exits 3 with
the PRE-degrau-6 compiler too, so it is not the wrapper's widening — a bind pattern over a `Named`
subject that is not a registered enum falls into "always matches", so the FIRST arm always wins.
That is this lane's disease in its purest form: not a stop, a silent wrong answer.

### An architecture hazard MEASURED here, not introduced here — the returned wrapper dangles

A variant wrapper is an `alloca`, i.e. a frame slot of the function that CONSTRUCTS it. A function
that RETURNS `T | error` therefore returns the address of its own dead frame, and the caller reads
tag/payload out of it. It survives the common shape (`match f(x) { … }` reads it before anything
else can write there) and it is measurably WRONG when a deep call intervenes:

```teko
let r = make(4)          // `-> []i64 | error`, or `-> Pt | error`
if noise(60) == 999999 { return 9 }   // 60 nested frames
match r { … }            // reads a clobbered wrapper
```

Measured with the STRUCT-payload version of that probe: the pre-degrau-6 compiler returns 0 and the
post-degrau-6 compiler returns 1. **Both are dangling; only the luck of the frame layout changed.**
The same probe with the wrapper built and matched in ONE frame passes either way. This is the
degrau-4 family (`NATIVE-AGG-SLICE-BY-ADDRESS`: an aggregate's value is the address of a frame
slot).

**RECLASSIFIED by the owner, 2026-07-28 — this is a BUG, not a decision.** It was recorded above as
an allocation-policy question awaiting a ruling. The ruling is that there is no question:

> *"A fuga, ocorreu por má implementação em native, em C funciona. Posse, já funciona hoje em C"*

The C route returns the same shape correctly. So there is no design to settle and nobody to wait
for — there is a native defect with a working reference implementation beside it. Whoever takes
this reads how the C route owns the wrapper and makes the native route agree.

### THE ORACLE RULE — general, and it outranks any single finding

**While the C route exists, any BEHAVIOUR divergence between native and C is a native bug until
proven otherwise. It is not an architecture question.** The C route is the reference implementation.

An architecture decision is warranted only when the two routes AGREE and are both wrong, or when the
construct has no C counterpart at all.

The rule was already doing the work twice today before it had a name — the declared-variant
miscompilation below (native 3, C 0) and this dangling wrapper. Naming it stops the next agent from
halting to request a ruling when reading the C route would have answered it.

**Measured exception, which is why the rule says "until proven otherwise" and not "always" — RE-MEDIDA,
ALARGADA e ESTREITADA em 2026-07-29 (secção "A ROTA C E O `null` EM COMPOSIÇÃO", no fim do ficheiro):**

O contra-exemplo registado aqui — `type M = variant Box | null` faz a rota C parar com
`codegen: cyclic value-type dependency` enquanto o nativo a executa correctamente — foi RE-MEDIDO e
**sustenta-se**. Mais: não é um caso isolado, é o membro visível de uma FAMÍLIA. O dono confirmou-o
no mesmo dia, corrigindo a sua própria formulação:

> *"na verdade eu quis escrever C, e acabei lhe dando a guia errada"* (dono, 2026-07-29, sobre
> *"tem um bug ... com composição cíclica quando ambas as variantes escrevem null"*)

**A família, tal como foi medida:** a rota C recusa TODA variante DECLARADA cuja lista de membros
contenha `null` — cíclica ou não, de dois membros ou de três, sozinha ou como campo de um `struct` —
sempre com a mesma mensagem `cyclic value-type dependency`, que na maioria dessas formas é um NOME
ERRADO para o que se passa (não há ciclo nenhum em `type M = variant Box | null`). A forma que o dono
descreve, `type A = variant B | null` com `type B = variant A | null`, é o membro CÍCLICO dessa
família. A forma INLINE das mesmas uniões compila e corre na rota C.

**Duas leituras que o registo anterior convidava, e que a medição não suporta:**

1. *"O nativo ganha em todo o `null` declarado."* Não ganha. Onde a variante-com-`null` é MEMBRO de
   outra variante, o nativo compila e devolve o BRAÇO ERRADO em silêncio — a rota C pára e o nativo
   mente, o que é pior do que parar. Esse defeito do NATIVO é independente do `null` e do ciclo (foi
   reproduzido com `error` e sem ciclo, com a rota C como oráculo a acertar) e está registado à parte.
2. *"A rota C está errada, logo o oráculo caiu."* Também não. Todas as falhas medidas na rota C são
   PARAGENS HONESTAS, com mensagem nomeada e exit 1 — a rota C nunca devolveu um número errado nesta
   vizinhança. É exactamente por isso que a regra diz *"bug do nativo ATÉ PROVA EM CONTRÁRIO"* e não
   *"sempre"*: a prova em contrário existe, tem nome, e recusa-se a compilar em vez de mentir.

### A CAUSA — e são DUAS metades, não uma

`checker::resolve_named` (`src/checker/resolve.tks:775`, arm `parser::TypeDecl`) mantém um tipo de
utilizador NOMINAL: `type Shape = variant Circle | Square` chega ao backend como
`checker::Named{"ns::Shape"}`, NUNCA como o `checker::Variant` que uma união INLINE `A | B` traz. E
todo o protocolo de união do backend casava em `checker::Variant`:

| metade | sítio (antes) | o que fazia com um `Named` |
|---|---|---|
| CONSTRUÇÃO | `lower_value_into_type` (`src/lir/lower.tks:2805`) | `_ => lower_expr` — **nenhum invólucro tag+payload era construído** |
| TESTE | `lower_named_bind_pattern_test` (`src/lir/lower.tks:4896`, `null => PatternTest{always=true}`) | "casa sempre" → **o PRIMEIRO braço ganha todos os sujeitos** |

Os dois erros CANCELAM-SE no braço 1: o bind do valor inteiro lê o payload não-embrulhado no offset
0, que é exactamente o que o `Circle` tem lá. Em qualquer outro braço, resposta errada e calada.

A hipótese registada pelo agente anterior ("um bind pattern sobre `Named` cai em casa-sempre") estava
CERTA mas era META-DE: corrigir só o teste teria trocado uma resposta errada por outra (o `tag@0`
lido de um `Circle` não-embrulhado é `7`, que não casa com braço nenhum).

### A CORREÇÃO — uma função, três sítios, uma tabela

`expand_named_variant(t, ctx.variants)` (`src/lir/lower.tks`) devolve a união que o `Named` declara.
Aplicada nos TRÊS pontos onde um tipo entra numa decisão de união — o sujeito do `match`
(`lower_match_subject`), o tipo DECLARADO da colocação e o tipo do VALOR colocado
(`lower_value_into_type` / `lower_value_into_null_union` / `lower_value_into_variant`) — para que
construção e teste leiam a MESMA lista de membros, na mesma ordem, da mesma tabela.

A tabela (`collect_variant_defs`, `src/lir/lower_const.tks`) expande cada corpo pelo resolvedor DO
CHECKER (`checker::resolve_type`, a mesma chamada que `checker::expand_variant` faz). **A armadilha
que custou um ciclo:** `checker::type_table_of` chaveia cada entrada pelo nome CANÓNICO (`p::Circle`)
com namespace vazio, e a regra R3 do resolvedor procura `entry.name == <bare> && entry.namespace ==
ref_ns` — contra essa tabela, TODOS os membros falham a resolver e o corpo cai num recurso nominal
sem qualificação. `declared_type_table` volta a partir o nome canónico em (bare, namespace), que é
como o resolvedor lê uma tabela; só assim os membros saem com o nome canónico que
`variant_member_type_matches` compara EXACTAMENTE (comparar por último segmento seria trocar um
silêncio por outro: dois tipos homónimos em namespaces diferentes deixariam de ser casos distintos).

A tabela SUBSTITUI a tabela só-de-nomes que o serializador de consts usava (`find_variant_info` →
`find_variant_def`): a etiqueta que uma imagem em rodata carrega e a etiqueta que um braço compara
já não podem vir de duas pesquisas diferentes.

## A ROTA C E O `null` EM COMPOSIÇÃO — medida com um CONTROLO real e uma fronteira numérica (2026-07-29)

Precisão do dono, no mesmo dia, sobre o alvo desta secção: *"existem no código e funcionam mas não
com null"*. Ou seja a composição cíclica de variantes DECLARADAS não é, em si, o que falha — ela
existe hoje no compilador e corre. O que falha é especificamente `null` como membro de uma variante
DECLARADA. Esta secção mede essa fronteira com um controlo, um par antes/depois no MESMO mecanismo, e
a causa exacta em `src/codegen/codegen.tks`.

### O CONTROLO — composição cíclica REAL, no código do compilador, que compila e corre hoje

`src/checker/type.tks:126` — `pub type Type = variant Prim | Byte | Char | Str | Slice | Optional |
Named | Variant | Func | Error | Void | Ptr | Uptr | Reference | Null` — é uma variante DECLARADA e é
CÍCLICA: vários dos seus membros são structs que guardam um `Type` de volta —
`Slice = struct { element: Type }`, `Optional = struct { inner: Type }`, `Variant = struct { members:
[]Type }`, `Reference = struct { inner: Type }` (`type.tks:86-114`). `Type` embebe `Optional` POR
VALOR (é um `union` C, ver adiante); `Optional.inner` é um `Type`, logo `Type → Optional → Type` é um
ciclo genuíno. Este tipo é usado em todo o checker e o compilador AUTO-CONSTRÓI-SE com ele — não há
medição mais forte de que funciona do que essa.

**Como o ciclo é quebrado (por que funciona):** `emit_type_decl` (`codegen.tks:9069`) emite uma
variante DECLARADA como `{ tag; union { membros POR VALOR }; }` — cada membro estrutural está
embebido inteiro dentro do `union`. O que quebra o ciclo é uma camada ABAIXO da variante:
`cg_field_boxed` (`codegen.tks:1457`), chamado ao emitir CADA STRUCT, testa se o campo "alcança de
volta" o próprio struct por valor (`cg_te_reaches_byvalue`, `codegen.tks:1391`) e, se sim, emite-o
como PONTEIRO em vez de valor. `Optional.inner: Type` alcança `Optional` (`Type` embebe `Optional`
por valor no seu `union`), logo o campo é boxed — `Optional` em C fica `{ bool present; tk_t_Type
*value; }`. Um struct SEM campos por resolver está sempre pronto (`cg_named_ready`,
`codegen.tks:9805`, ramo `StructBody`, `codegen.tks:9814`: um campo boxed é saltado, não testado);
por isso `Optional` fica pronto antes de `Type`, e `Type` fica pronto assim que todos os SEUS membros
(incluindo `Optional`, já pronto) estiverem prontos. O ciclo fecha por baixo, no campo do STRUCT, não
na variante.

### O fixture mínimo que isola o MESMO mecanismo — antes (controlo) e depois (só `null` acrescentado)

Dois projectos standalone, mesma forma que `checker::Type`/`Optional` (`Node → Wrap_c → Node`, quebrado
pelo mesmo `cg_field_boxed`), compilados com o compilador construído a partir do SOURCE actual
(`.gen1c`, ver "O compilador usado" no fim desta secção).

**ANTES — `cyc_control` (sem `null`), `src/probe.tks`:**

### UM CICLO DIRECTO variante↔variante (sem struct a quebrar) É OUTRA FALHA, genuína, e não tem
### `null` nenhum — para não confundir as duas

```teko
pub type Circle = struct { r: i32 }
```

Sem `null` em lado nenhum, sem struct a mediar — `A` embebe `B` por valor DENTRO do seu `union`
(`emit_type_decl`, `VariantBody`), `B` embebe `A` da mesma forma, e não há campo de STRUCT ali para
`cg_field_boxed` boxar — o mecanismo que quebra o ciclo do controlo simplesmente não está presente
nesta forma. Falha com a MESMA mensagem `codegen: cyclic value-type dependency`, e aqui a mensagem
ESTÁ CERTA: é um ciclo por valor genuíno, sem quebra possível, exactamente o que o próprio texto da
mensagem descreve (*"a recursive type must pass through a slice or a boxed reference"*). Isto é
esperado e correcto, e é uma falha DIFERENTE da do `null` — fica registado para que ninguém a
confunda com a família medida acima só porque a mensagem é literalmente igual.

### A CAUSA EXACTA — `src/codegen/codegen.tks`, o sítio onde `cyclic value-type dependency` nasce

A mensagem em si (`codegen.tks:10076`) é só o veredicto final de um ponto fixo
(`cg_emit_types_ordered`, laço a partir de `codegen.tks:9997`): emite tudo o que já está PRONTO, repete
enquanto houver progresso, e se sobrar algo por emitir (`remaining > 0`) chama isso de "ciclo". A
mensagem é honesta quando o motivo É um ciclo — e ERRADA quando não é, porque "pronto" está a ser
calculado mal para um caso que não é cíclico nenhum.

O ramo que decide se uma variante DECLARADA está pronta é `cg_named_ready`
(`codegen.tks:9805`), ramo `parser::VariantBody` (`codegen.tks:9821-9832`):

```
parser::VariantBody as vb => match vb.type_expr {
    parser::UnionType as u => {
        mut i = 0
        loop {
            if i >= u.members.len { break }
            if !cg_texpr_ready(prog, em, set, u.members[i], owner_ns) { return false }
            i++
        }
        true
    }
    _ => true
}
```

Este ramo pergunta, membro a membro, `cg_texpr_ready` sobre o TYPE-EXPR SINTÁTICO de cada membro. O
membro `null` chega aqui como um `parser::NamedType` de um único segmento `"null"` — é assim que o
parser representa o átomo `null` numa posição de tipo (`src/parser/parse_type.tks:36-43`, doc: *"`Null`
unit type; it is carried as a single-segment `NamedType` named 'null'"*).

`cg_texpr_ready` (`codegen.tks:9780-9803`) trata um `parser::NamedType` assim:

```
parser::NamedType as nt => {
    let base = nt.path.segments[nt.path.segments.len - 1].name
    if cg_is_builtin_scalar(base) { return true }
    if cg_is_class_named(prog, base) { return true }
    if nt.args.len > 0 { return cg_named_emitted(em, cg_texpr_inst_name(base, nt.args)) }
    let want = match cg_find_decl_ns(prog, nt.path, owner_ns) { parser::TypeDecl as dd => dd.name; error => base }
    cg_named_emitted_precise(prog, em, want)
}
```

`cg_is_builtin_scalar` (`codegen.tks:9743-9749`) lista `u8..u64, i8..i64, f32, f64, bool, byte, str,
error, ptr, uptr, Ref` — **`"null"` NÃO está nesta lista.** Não é uma classe (`cg_is_class_named`
falha), não tem argumentos genéricos, então cai em `cg_find_decl_ns(prog, nt.path, owner_ns)` — uma
procura por um `parser::TypeDecl` chamado `"null"`. NUNCA existe um `type null = …` declarado em
programa nenhum — `null` é uma palavra reservada, não um tipo nomeável — logo essa procura falha SEMPRE
(`error => base`) e `want` fica `"null"`. `cg_named_emitted_precise(prog, em, "null")` pergunta se
`"null"` já está na lista de nomes emitidos — e NUNCA vai estar, porque nada com esse nome é alguma vez
emitido. **`cg_texpr_ready` devolve `false` para sempre**, para qualquer variante DECLARADA que tenha
`null` como membro sintáctico — independentemente de haver ciclo, independentemente de quantos outros
membros existam, independentemente de qual dos dois lados de um par o carrega.

Consequência no ponto fixo: essa variante nunca fica "pronta", `remaining` nunca chega a 0, o laço pára
por falta de progresso, e a mensagem `cyclic value-type dependency` dispara — a MESMA mensagem de um
ciclo genuíno (a secção anterior), mas por uma razão totalmente diferente: não é um ciclo, é uma procura
por um tipo chamado `"null"` que não pode nunca ter sucesso.

**Por que o compilador SABE distinguir `null` num outro sítio, e não aqui:** existe um segundo caminho,
`cg_texpr_union_ready` (`codegen.tks:9769-9778`), chamado só a partir do ramo `parser::UnionType` de
`cg_texpr_ready` (`codegen.tks:9800`) — ou seja, quando um `null` aparece dentro de uma união INLINE
numa posição de CAMPO (`child: Tree | null`, o padrão do próprio corpus em
`examples/regressions/bulk/src/q013_recursion_through_a_variant_payload_s/body.tks:7`). Esse caminho
chama `cg_texpr_union_has_null` (`codegen.tks:2366-2379`) PRIMEIRO e trata a união null-bearing pela
sua representação RESOLVIDA (niche / box-in-arena / wrapper), nunca tentando resolver `"null"` como um
nome de decl. **O ramo `VariantBody` de `cg_named_ready` não passa pelo `UnionType` de `cg_texpr_ready`
— ele itera `u.members` directamente e chama `cg_texpr_ready` em CADA membro isolado.** Um membro
isolado `null` nunca é visto como parte de uma união com null — é visto como um `NamedType` solto, e
cai na procura de decl que nunca resolve. É a mesma assimetria, em código: a posição de CAMPO sabe o
que fazer com `null`; a posição de MEMBRO DE VARIANTE DECLARADA não sabe.

### Regression measured, and RETRACTED — not a narrow-scope story, a bigger one

A corpus member (`f_declared_variant_push_in_loop`, `examples/regressions/own_native/src/corpus.tks`)
pushing a declared variant of `struct` payloads in a loop, then indexing back and reading a field, was
written, and it CRASHES natively (SIGSEGV) — while the C route exits 0/42 cleanly. Root-caused (gdb,
`x/40i $pc`, `info registers` on the generated ELF — no DWARF, no `cc`-built symbols, this is the
native backend's own object writer) to the SAME hazard this doc already named and reclassified as a
bug under degrau 8, above ("An architecture hazard MEASURED here... the returned wrapper dangles"):
the pushed item is `dv_pick(i)`'s RETURN VALUE — a `Named`/`Variant` value IS the address of an
`alloca` in the CALLEE's own frame (§5.1) — and `box_aggregate_value`'s `tk_slice_elem_box` copy of
that 24-byte wrapper, which runs in the CALLER after `dv_pick` has already returned, can read STALE
bytes if anything intervenes between the two calls. It is NOT specific to this degrau's fix (the fix
only made a declared-variant push COMPILE; the dangling-wrapper defect pre-dates it and was already
on record) and it is NOT this degrau's to fix — see the "wrapper dangles" section above for the
owner's ruling on it and for what the fix needs (make the CALLER own the returned aggregate's storage,
the way C's hidden-return-pointer ABI already does — an ABI-level change, not a lowering arm).

**What is new here, worth recording precisely:**

- **Positional, not type-specific.** `type DvShape = variant DvCircle | DvSquare | DvTri`, push+read
  the FIRST-declared case (`DvCircle`, tag 0) — crash. Swap the declaration order
  (`DvSquare | DvCircle | DvTri`) and push+read `DvSquare` first instead — SAME crash, same tag 0.
  The SECOND and THIRD declared cases (tag 1, tag 2) read back correctly in every ordering tried.
- **Reading the field is what faults, not the push, not the match, not the bind.** Isolated with a
  10-line probe (`teko run`): `xs = push(xs, dv_pick(0)); match xs[0] { DvCircle as c => {} ... }`
  (no field read) — exits cleanly. Add `if c.r != 7 { ... }` — SIGSEGV. The crash instruction (via
  gdb) dereferences the payload pointer LOADED FROM the boxed wrapper's own copy — that copy's
  payload-pointer word holds garbage, not the address `store_scalar_variant_payload` wrote at
  construction (confirmed correct in isolation: `let y = dv_pick(0); match y { DvCircle as c => if
  c.r != 7 {...} }`, no push at all, reads back fine for every case).
- **NOT narrow.** A 2-member variant (`DvPushA | DvPushB`), verified crash-free in an ISOLATED
  8-line probe project, STILL crashes once the identical shape is pasted into
  `examples/regressions/own_native/src/corpus.tks` alongside the corpus's other ~30 functions. This
  matches this doc's own words from the first time this hazard was measured — *"Both are dangling;
  only the luck of the frame layout changed"* — and it means the hazard's trigger rate depends on
  the WHOLE compilation unit's register pressure, not on the isolated construct. It cannot be
  dodged by picking a "safer-looking" shape; there is no shape this backend can currently GUARANTEE
  safe.
- **On the MInst critical path.** `MInst`'s own members are all `struct`s, `push_minst_block` is
  exactly this shape, and the compiler's own encode functions read fields off instructions blocks
  hold (`inst.dst`, `inst.imm`, …) constantly. Once degrau 9 (and whatever sits behind it) clears
  far enough for the self-build to start EXECUTING code that pushes and later reads an `MInst`, this
  is the crash it will hit — non-deterministically, by the same "luck of frame layout" logic.

**Retraction, and why:** the regression that exposed this was REMOVED from the corpus
(`git checkout -- examples/regressions/own_native/`) rather than committed. A corpus member whose
pass/fail depends on the surrounding file's register allocation is not a regression test, it is a
coin flip that would make `teko test .` flaky by CI machine/compiler-version rather than by code
change — exactly the kind of gate the standing rules forbid weakening. The corpus is left exactly as
`main` has it; only `src/lir/lower.tks` (the `variant_payload_box_bytes` correction above) changed.

**This is reported, not fixed, deliberately.** It needs the ABI-level fix the "wrapper dangles"
section already scoped (make the callee write an aggregate/variant return DIRECTLY into caller-owned
storage — a hidden output-pointer parameter, mirroring what C's own calling convention already does
for a large/aggregate return) across EVERY aggregate-returning function, not only variant
constructors. That is substantially larger than "verify degrau 8" and it is a pre-existing defect
this session did not introduce — it was already named and ruled a bug by the owner before this cargo
started. What this session adds is proof that it is not a rare corner: it is reachable from the most
ordinary shape a declared variant offers (construct in a callee, push, read a field), it is positional
rather than type-bound, and its trigger rate is a whole-file property. It should be prioritized
alongside or ahead of degrau 9, because clearing compile-time stops without it only trades a loud
build failure for a silent runtime crash once the self-build starts exercising the values it
constructs — which is exactly what self-hosting requires.

#### The cause

`resolve_generic_inst` (`src/checker/resolve.tks`) stamps a generic instance's canonical name as
`generic_inst_name(base, args)` = `"<base>__g__<arg0>[__<arg1>…]"`, where `base` is the WRITTEN
path's BARE LAST SEGMENT (never namespace-qualified, `qualify`'s own doc: "generic `__g__`
instances stay bare") and each `arg` is ALSO reduced to its own bare form by `type_mangle`. The
result — `Parsed__g__MainFile` — contains **zero** `"::"` separators, ever, by construction.

`variant_member_named`'s `Named` arm compared `checker::name_last_segment(n.name) == case_name`.
`name_last_segment` finds the LAST `"::"` and returns everything after it, or the WHOLE string
unchanged when there is none. A generic instance's name has none, so the compare was
`"Parsed__g__MainFile" == "Parsed"` — always false. A bind pattern's case name
(`bind_pattern_case_name`) is always the pattern's BARE base (`Parsed`) — a pattern's type-args are
carried in the SEPARATE `bp.type_args: []parser::TypeExpr` field, never folded into the name — so
the two sides could never agree for ANY generic member, regardless of namespace or arity (exactly
what the repro table shows).

The checker's OWN exhaustiveness code had already solved an ADJACENT version of this
(`checker::match.tks::bind_case_name`: when a pattern carries explicit type-args, resolve the FULL
instance name and compare THAT), which is why the construction side and the checker's typing of
the match arm were never in doubt — only this backend's OWN, separately-implemented case lookup
had the gap.

#### The fix (`src/checker/resolve.tks`, `src/lir/lower.tks`)

`checker::split_generic_instance_name(name)` scans ONCE for the `__g__` stamp and returns
`{ is_generic, base }`. `checker::named_case_name(name)` delegates to the BASE for a generic
instance and to `name_last_segment` otherwise. `variant_member_named`'s `Named` arm now compares
`named_case_name(n.name) == case_name`.

**Why base-name matching and not full instance-name matching.** The pattern side has NO resolved
type to build a full instance name from at lowering time (`LowerCtx` carries no `TypeTable`/
`ref_ns`, unlike the checker's exhaustiveness pass) — reconstructing one would mean mangling
arbitrary written `TypeExpr`s (including nested generics) by hand, a MUCH larger change for a
capability nothing in the compiler's own source uses. Matching the pattern's bare base against the
member's bare base is the narrow fix that closes `asm_parse` and every construct like it.

**The ambiguity this narrowing accepts, and why it is not silent.** A base name is not necessarily
unique within one union: `type M = variant Box<i64> | Box<str>` is LEGAL Teko (measured: the C
route — the oracle — accepts it and picks the right arm by VALUE), and both members would answer
the pattern's bare base `Box` identically. Rather than resolve the ambiguity by always taking the
FIRST match (which would silently miscompile the SECOND case, every time, for any variant with two
same-base instantiations) — THE LAW this lane is under ("if the correction makes it compile and
lie, stop") — `find_variant_member` now scans every member, and a SECOND match whose full canonical
name differs from the first (`generic_case_ambiguous`) is refused with a named, honest stop
(`"ambiguous variant case \`<name>\` — more than one member shares this generic base (internal)"`)
instead of a guess. This construct exists NOWHERE in the compiler's own source today (searched: no
union/variant declares two instantiations of the same generic base) — the guard costs nothing on
the self-build and prevents a landmine for the general language.

#### The fix, three memory shapes, because this backend already gives `mut` locals three different ones

**Read** (`src/lir/lower.tks`, `lower_ref_deref_read`/`lower_ref_deref_read_fat`, gated by the new
shared `is_ref_deref` predicate ahead of `lower_field_access`'s/`lower_fat_field`'s struct-layout
path): the handle's own value already IS the address — a REGISTER-value `T` (`is_register_value_
type` — every primitive/`byte`/`enum`) is genuinely stored there and must be LOADED; an AGGREGATE
`T` is, in this backend's own memory model, ALREADY represented BY its address
(§ NATIVE-AGG-SLICE-BY-ADDRESS — the SAME model degrau 4 named), so the deref is a PASSTHROUGH of
the handle's own VReg, not a load (loading eight bytes from that address would read the pointee's
OWN first field, not its address). A FAT `T` reads both halves through `load_fat_slot` at the
handle's address (the exact shape a mutable fat local's own frame slot already uses).

**Write** (`lower_assign_ref_deref`, replacing the stop `lower_assign`'s `RefDeref` arm named): the
SAME three-way split. FAT writes both halves through `store_fat_slot` at the handle's address
(`store_assign_fat_ref`). REGISTER-value `T` reuses `store_assign_value` VERBATIM — the exact
function a struct FIELD write's own scalar arm already uses (a compound `op=` and a union-wrapping
plain `=` come along for free, no new code). **AGGREGATE `T` needed a genuinely NEW arm
(`store_assign_aggregate_ref`), and this is the second silent-miscompile trap the lane's own law
against "compile and lie" caught red-handed**: the naive stand-in — routing an aggregate through
`store_assign_value` too, exactly like a struct FIELD's aggregate half already does — COMPILED AND
RAN, printing `answer=42!`, and returned the WRONG exit code (measured: 50, not 42) instead of
crashing or refusing. Why: a struct FIELD of aggregate type is, in this backend, a BOXED pointer
SLOT (the field genuinely holds an address to a separately-allocated instance) — but `Ref<T>` is
not a slot, it names `T`'s OWN memory directly (the C route's bare `<T> *`), so storing the new
value's address there overwrites the pointee's own first bytes with a pointer instead of its data.
The fix `memcpy`s the new value's bytes (its own lowered address) into the handle's pointee
storage, sized by the SAME whole-type byte width degrau 4/6's `aggregate_box_bytes` already
computes for push-boxing — one new one-line runtable entry, `tk_mem_copy` (`teko_rt.c`/`.h`),
mirroring degrau 4's OWN precedent and reasoning for touching the runtime ("the LIR has no
memcpy/allocation op").

**Call-site auto-ref** (`lower_call_args`/`lower_args_ref_aware`/`lower_addr_of_arg`, intercepting
`lower_call` BEFORE the plain `lower_args`): a NEW whole-program table, `LRefFnInfo`
(`collect_ref_fns`, built once alongside `enums`/`variants`), records which parameter POSITIONS of
which top-level functions are `ref` — read straight off `parser::Param.type_ann` (`NamedType
"Ref"`), the SAME syntactic test `codegen.tks::emit_call` already runs, agreed with rather than
re-derived. At a call whose callee has a `ref` parameter, the matching NON-forwarded argument
(`arg_needs_auto_ref` — a value already `Reference`-typed, a forwarded `ref`, needs no change) is
lowered to its ADDRESS instead of its value, split three ways matching the read/write split:

- a FAT (`str`/`[]T`) local's address ALREADY EXISTS unconditionally — `mut s: str = …` is
  frame-slot-bound the moment it is declared (`bind_mutable_fat`, the list-builtin degrau,
  independent of `ref`) — `lenv_lookup_fat_slot`'s hit IS the address to pass. **This is the THIRD
  silent trap measured red-handed**: the first working draft of the call site fell back to
  `lower_expr` for anything not a bare register value, which for a fat `TVar` gives the STRING'S
  OWN ptr VALUE (the content pointer) — a probe (`rd_set_msg(s, "hello")`) compiled, linked, and
  **segfaulted** the moment it wrote through that wrong "address";
- an AGGREGATE local's own VReg already IS its address (no new work, same read-side reasoning);
- a REGISTER-value local (the ACTUAL blocking case: `checker_tick_fn`'s two `ref<u64>` params) has
  NO address of its own — ordinary `mut` scalars live in pure SSA VRegs, rebound on write
  (`lenv_reassign`), never addressed. **This is the keystone new piece**: a whole-function PRE-PASS
  (`collect_addr_taken_locals`, an exhaustive statement/expression walker — every `TStatement`/
  `TExpr` shape, including nested calls, lambda bodies, and match/if arms) finds every scalar local
  name EVER passed as a `ref` argument ANYWHERE in the enclosing function, BEFORE any of its
  statements lower. Such a name binds to a fresh ONE-WORD frame slot at its OWN binding site
  (`lenv_bind_scalar_slot`, `bind_addr_taken_scalar` — the FOURTH `LEnv` binding shape, alongside
  plain/fat/fat-slot), and EVERY access of it (`lower_var`'s read, `lower_assign_simple`'s write —
  which now checks `lenv_lookup_scalar_slot` FIRST and, on a hit, reuses `store_assign_value` at
  that address instead of `ctx_reassign`) goes through that memory for the rest of its lifetime.
  The slot's ADDRESS threads through loop/if merges exactly like a mutable fat local's own slot
  address already does (`rebind_promoted`'s THIRD branch) — over-approximating on purpose (a name
  that is really a nested lambda's own shadow may be reified needlessly; the cost is one harmless
  indirection, never a wrong answer) rather than resolving lexical scope precisely.

#### A NATIVE-BACKEND BUG FOUND AND FIXED IN SCOPE — a call site off by 8 bytes of stack alignment

Proving the `d`/`n`-int family by VALUE (not merely by successful compilation) surfaced a SECOND,
unrelated defect: a native-compiled corpus fixture using `:D`/`:N` **crashed at runtime** —
`SIGSEGV` inside glibc's `__printf_buffer_init`, several frames below `tk_fmt_d`'s own `snprintf`
call — while the IDENTICAL C-route build ran correctly. This is exactly the standing law's trap
("if the fix makes it compile and lie — or crash — instead of stopping honestly, STOP and
report"), so it was chased to its root rather than narrowed away by excluding `d`/`n` from the
fixture.

**Root cause, confirmed with `gdb`, not guessed**: the crash's own frame showed
`rsp % 16 == 8` at the fault — an ABI violation. Tracing it to its source: the native entry stub
`wrap_native_entry` appends (`argc`/`argv` → `tk_set_args` → the renamed virtual-main → its own
`ret`) has ZERO local frame slots and clobbers ZERO callee-saved registers, so
`frame_sub_size_x86`/`frame_is_framed_x86` (`encode_x86_64.tks`) judged it "frameless" and emitted
NO prologue/epilogue at all — meaning RSP stayed at its ABI-guaranteed ENTRY value (`rsp+8 ≡ 0 mod
16`, i.e. `rsp ≡ 8`) through EVERY call this stub itself issues, off by exactly the 8 bytes SysV
requires be corrected before a `call`. This has been true since degrau 1 — every native-compiled
program's own process entry has carried this off-by-8 stack for its two outermost calls — and
stayed invisible because NOTHING previously called from that point ever dipped deep enough into
alignment-sensitive code (glibc's more elaborate `vsnprintf`/`vfprintf` internals, first reached
natively by THIS degrau's own `tk_fmt_d_len`/`tk_fmt_n_i_len`) to fault on it.

**Why `frame_is_framed_x86` missed this**: its own three-part test (`size>0` OR any callee-saved
register) never asked "does this function make a call at all" — the ONE question that matters for
alignment, independent of local storage. ARM64's own `compute_frame_layout` (`encode_arm64.tks`)
already asks an ADJACENT question for an ADJACENT reason: `needs_lr_save = func_any_call(f) &&
func_any_ret(f)` forces a frame whenever a function calls AND returns (so LR survives the call to be
read again) — but AArch64's `BL` never touches SP at all, so ARM64 was never exposed to this
specific alignment bug; only x86-64's implicit "the `call` instruction pushes a return address"
convention makes a genuinely frameless-yet-calling function unsafe.

**The fix, narrowly scoped to the EXACT axis that matters — mirroring arm64's OWN two-part test,
not just porting "makes a call"**: a NAKED existing unit test,
`ex_func_frameless_call_reloc` (`encode_x86_64_test.tkt`), already asserts BYTE-FOR-BYTE that a
frameless function whose ONLY instruction is `call tk_exit` (a call with NO `ret` anywhere — this
backend's own `exit(n)`-terminated program shape) encodes with ZERO prologue/epilogue bytes. That
shape is SAFE exactly because nothing ever returns to observe (or need) the restored alignment — a
program that never returns from its outermost frame cannot itself be harmed by a misaligned single
call, and re-framing it would have been an UNMOTIVATED behavior change with no bug behind it. The
fix therefore adds `needs_call_align_x86(f) = func_makes_call_x86(f) && func_any_ret_x86(f)` (a new
`func_any_ret_x86`/`block_any_ret_x86` pair mirroring arm64's own `func_any_ret`/`block_any_ret`),
threaded through a new `FrameLayoutX86.call_align` field that `frame_is_framed_x86` now also
consults. When `call_align` is the ONLY true condition, the emitted frame is the minimal
`push rbp; mov rbp,rsp` (no `sub rsp` — `size` stays 0, correctly) paired with a bare `leave` —
restoring exactly the missing 8 bytes at zero extra runtime cost, and touching NOTHING for every
function that was already framed for an independent reason (their `size`/saved-register conditions
are unchanged, so their encodings are byte-identical to before this fix).

**Why the runtime was touched, again**: consistent with degrau 4/18's own precedent and reasoning —
each `_len` twin is a thin wrapper the LIR's own `lower_len_out_call` convention needs because this
backend's `LCall` captures one result register, not the two-eightbyte struct a real `tk_str` return
occupies; no format/scan logic was duplicated.

### Why a bare alias, not a runtime call — measured, not assumed

`f64_bits(f: f64): u64` and `f64_from_bits(u: u64): f64` reinterpret an 8-byte IEEE-754
bit pattern with NO arithmetic. `LConstFloat` (`src/lir/lir.tks:50`) already carries a float
literal as its raw `bits: u64` rather than an f64 value, and this backend's VRegs carry no
run-time type tag of their own (a value's machine class lives only in the ONE instruction that
defines it and in whatever type each CONSUMING instruction independently declares) — so the
identity bit pattern crosses the `f64`/`u64` boundary with no instruction at all, only a
re-labeling of which LIR expression owns the VReg going forward. `lower_call`
(`src/lir/lower.tks`) now intercepts `teko::f64_bits`/`teko::f64_from_bits` BEFORE
`call_symbol` resolution (`is_f64_bitcast_call`/`lower_f64_bitcast_call`, the same molde
`is_err_loc_call`/`lower_err_loc_call` degrau 22 already used for a call the runtime resolver
cannot see), returning the argument's own advanced context and VReg unchanged — so
`native_builtin_symbol` never sees either name and needs no new table entry.

A real `LCall` to `tk_f64_bits`/`tk_f64_from_bits` was tried FIRST and measured, not assumed
adequate: the f64-class argument/result would have to travel through XMM per the SysV/Win64
ABI, and `pin_args_x86`/`select_call_result_x86` (`src/codegen/isel_x86_64.tks`) are still
GPR-only pending the separate `B1-fp` float-register-class family. A scratch repro built
exactly that call shape and measured a real corruption: with two live `f64_bits`/`f64_from_bits`
results at once, both silently read back whichever bit pattern last happened to sit in the
single physical XMM0, not their own. The bare-alias fix sidesteps the gap entirely rather than
landing on top of it — ordinary GPR register allocation, which already keeps any number of
plain integer values alive correctly, carries every one of the reinterpreted values to its own
read-back untouched.

### Fixture — `f_f64_bits_roundtrip` (code 100, `examples/regressions/own_native/src/corpus.tks`)

Round-trips THREE runtime-selected bit patterns (including a negative magnitude, sign bit set)
through `f64_from_bits` then back through `f64_bits`, with all three producer values kept LIVE
AT THE SAME TIME — the exact shape that the measured scratch repro showed would silently
corrupt under a real-call lowering. Values are built from a plain `i64` `tag` rather than an
`f64` literal/ALU op/compare, since every other path onto an `f64` VALUE belongs to the separate
`B1-fp` honest-stop family this fixture does not exercise.

## Degrau 25 — CLOSED: two placements had no declared type to coerce against, and only ONE of them stopped

**Branch**: `cargo/0.3.1.0-degrau-25`, off `remodel/0.3.1.0-linux-native-2` @ `5fb6b39f`.

### The stop this closes

```
teko: .: native backend N1: a `null` in this position needs the null-union wrapper the placement does not declare a type for (N2) [in `teko::checker::resolve_generic_inst`]
```

Reproduced through the full route before anything changed (gen1 from the committed `bootstrap/teko.c`
→ `.gen1b` C-route rebuild → native self-build), then narrowed to ten lines in 1.7s:

```teko
pub type Holder = struct { inner: i64 | null }
pub fn probe(): i32 {
    let h = Holder { inner = null }
    match h.inner { null => 0; i64 => 1 }
}
```

The compiler's own site is `resolve_generic_inst`'s `return Ptr { inner = null }`
(`src/checker/resolve.tks`) — a struct-literal FIELD whose declared type is `Type | null`.

### The message was HONEST about itself, and the doc beside it was NOT

`lower_null_lit`'s stop said exactly what was wrong (the placement declares no type), and it is
genuinely `N2`. What lied was `lower_value_into_type`'s own doc, which claimed the two placements
carrying no declared type — a call argument and a struct-literal field — *"are closed at the other
end instead, by `lower_null_lit`'s honest-stop, so no placement can write a raw `const 0`"*.

**Only the field was closed.** Measured, C route as the oracle:

| probe | native | C route |
|---|---|---|
| `Holder { inner = null }` | the honest stop | 0 |
| `Holder { inner = 5 }` then `match` | **SIGSEGV** | 0 |
| `take(null)`, `take` taking `i64 \| null` | **SIGSEGV** | 0 |
| `take(9)`, same signature | **SIGSEGV** | 0 |

The asymmetry has a cause, and it is the lane's own dominant pattern — **twins that diverged**. A
struct-literal field value IS typed against its declared type (`type_value_expected`'s `NullLit`
arm gives it `checker::Null`), so its bare `null` reaches the stop. A call ARGUMENT is typed with NO
expected type at all (`type_call` calls `type_expr` and then shallow-retypes), so its bare `null`
carries the LEGACY `Optional{Void}` bare-null sentinel, walks straight past a stop that only tests
for `checker::Null`, and lands on a raw `const 0` the callee's own `match` reads as the wrapper's
base address. And a bare `T` in EITHER placement was never even a candidate for that stop: it was
simply stored unwrapped.

**A stop that fires for one of a family's four members is worse than no stop at all**, because it
certifies the other three. That is the lesson of this degrau, and it is why the fix was not "widen
the stop".

### The fix — give both placements the declared type the C route already had

The C route has never had this defect: `emit_struct_init_literal` looks the field's declared
annotation up (`cg_find_struct_field_type`) and lets it drive the null-literal form. The own
backend now has the same two lookups.

| piece | file | what it is |
|---|---|---|
| `LFieldDecls` + `collect_field_decls` / `field_decls_of` / `resolved_field_type` | `src/lir/lower.tks`, `src/lir/lower_const.tks` | the checker-typed COMPANION of the layout table: each field-shaped declaration's field annotations resolved through `checker::resolve_type` over `declared_type_table`, keyed by the SAME canonical name `find_struct_layout` probes. A `class` contributes its EFFECTIVE instance fields, so an inherited field coerces like an own one |
| `LowerCtx.field_decls` | `src/lir/lower.tks` | threaded read-only exactly like `variants`/`ref_fns` (9 `LowerCtx` literal sites, `lower_program` → `lower_item` → `lower_item_function` → `lower_function`, plus `lower_virtual_main`) |
| `find_field_decl_type` / `field_type_in_decls` / `union_field_placement` | `src/lir/lower.tks` | the store site's lookup. An annotation that did not resolve answers `Void` → reported as "no declared type" → the value lowers plainly, exactly as before the table existed |
| `store_struct_field` | `src/lir/lower.tks` | THREE shapes now, and the UNION one is decided FIRST: a union field holds ONE word (the wrapper's address), so it must be decided before the fat arm — a `str \| null` field is not fat even though a `str` value flowing into it is |
| `callee_param_types` / `param_type_at` / `lower_arg_into_param` | `src/lir/lower.tks` | the argument half, off `TCall.callee_type` (the `Func` the checker attaches to a direct, method, closure or interface-dispatch call). EMPTY for a callee the checker left untyped (a builtin, a generic instantiation) and for a VARIADIC callee, whose trailing args do not pair with declared params — an empty list coerces nothing, i.e. keeps the previous behaviour rather than guessing |

**Design reference: Rust**, and specifically its surface property that a literal's type comes from
its placement's expectation, by ONE mechanism, at EVERY placement. Teko already had that mechanism
on both sides of the phase boundary (`type_value_expected`/`retype_literal` in the checker,
`lower_value_into_type` in the lowering); what it did not have was every placement using it. No new
concept was introduced — two placements were connected to the one that already existed.

**Method-call alignment was verified, not assumed:** an instance method's `callee_type.params[0]` IS
the receiver and `c.args[0]` IS the receiver, so `params[i]` pairs with `args[i]` at every index —
a probe with a `self` receiver plus a `i64 | null` second parameter round-trips both the `null` and
the present case on both routes. The interface-dispatch path's `lower_args_from(…, start=1)` pairs
the same way for the same reason (its `params[0]` is the receiver it skips).

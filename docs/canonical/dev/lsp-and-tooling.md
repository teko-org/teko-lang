# The LSP Server, Editor Clients, and Developer Tooling

Teko ships its editor intelligence as a **native subcommand of the compiler itself**,
`teko lsp`, plus a family of sibling native subcommands (`fmt`, `doc`, `lint`, `repl`) that all
reuse the same lexer/parser/checker the main compiler is built from. None of this is a separate
project or a separate language runtime — it is the compiler, addressed differently.

## `teko lsp` — the language server

`teko lsp` speaks JSON-RPC 2.0 over stdio (`teko::lsp`, `src/lsp/`) and calls the compiler's
own front end **in-process**: `teko::lexer::tokenize`, `teko::parser::parse_module`,
`teko::checker`, `teko::fmt::format_source`. There is no separate analysis engine to keep in
sync with the compiler — a diagnostic the server reports is produced by literally the same
type checker that a `teko build` would run.

Capabilities:

- **Live diagnostics** — `didOpen`/`didChange`/`didClose` drive `publishDiagnostics`, sourced
  from the checker's own structured diagnostic stream (the same one `warnings.tks` and
  `diagnostics.tks` feed everywhere else in the compiler).
- **Formatting** — in-process calls into `teko::fmt::format_source`, so "format on save" never
  shells out to a second process.
- **Hover and go-to-definition** — driven by a symbol index built directly from the parsed AST
  (doc-comments are already preserved on declaration nodes, so hover text costs nothing extra
  to produce).
- **Completion** — the same symbol index plus the keyword table.
- **Semantic tokens** — richer, LSP-native syntax highlighting layered on top of the baseline
  TextMate grammar (below), keyed off the checker's actual type information rather than lexical
  guessing.

### Incremental model

A keystroke re-parses only the edited buffer for fast, local feedback; a full re-check (the
same `type_program` pass a build runs) happens debounced, on save — this two-speed model is
what keeps typing latency low without asking the type checker to become incremental internally.

## Editor clients

The server is editor-agnostic (stdio JSON-RPC); a thin, conventional `LanguageClient` wires it
into each editor. This client layer is necessarily written in each editor's own extension
language (TypeScript for VS Code, Vimscript/Lua for Vim/Neovim, Emacs Lisp for Emacs) — this is
glue code around a third-party editor's extension API, the same category as any editor's
`.vim`/`.el`/`.nanorc` support files, not a violation of "Teko-only": the *product* (the
language server, the compiler, the stdlib) stays entirely Teko; only the unavoidable
editor-specific wiring is written in the editor's own language.

- **VS Code** — a full extension: TextMate grammar for baseline coloring, a `LanguageClient`
  wired to `teko lsp`, and build/run/test task integration.
- **Vim/Neovim, Emacs** — the same `LanguageClient`-over-stdio wiring in each editor's
  idiomatic form.

### Syntax highlighting: two layers

- **TextMate grammar** (`tooling/shared/grammar-spec.json`, generated by `tm_gen.tks`) — a
  single source of lexical truth shared across every TextMate-consuming editor, avoiding the
  classic four-divergent-copies problem. Covers keyword classes, types, functions, namespaces,
  attributes (`#test`, …), and contextual keywords (`ref`/`adopt`/`unsafe`).
- **LSP semantic tokens** — a second, richer layer available once the server is connected,
  built from real type information rather than lexical pattern-matching (a variable resolved to
  a class instance colors differently from an unresolved identifier, which no TextMate grammar
  can express on its own).

### Validating the editor experience

A `.tkt` unit test cannot exercise "does hover actually render in VS Code" — that is validated
by driving a **real editor**: a headless VS Code (`@vscode/test-cli`/`@vscode/test-electron`,
or a web-server VS Code plus browser automation) with the extension loaded, asserting through
the editor's own extension API (or, for the visual flavor, browser automation against a
web-server VS Code) that hover, completion, live diagnostics, and formatting actually appear.
This runs as a dedicated, non-blocking CI job — real editor downloads and a browser are too
heavy to justify on every push, but light enough to run on a schedule/PR-label basis.

## Sibling native subcommands

| Subcommand | Purpose | Built on |
|---|---|---|
| **`teko fmt`** | The canonical formatter — zero-option, gofmt-style: there is exactly one formatting of any program. `--check` is a CI gate; comment re-attachment (comments aren't AST nodes) reconciles the token stream against the formatted output. Proven idempotent (`fmt(fmt(x)) == fmt(x)`) and behavior-preserving over the whole compiler's own source tree. | Parser/AST |
| **`teko doc`** | A documentation generator: walks `pub`/`exp` items and their doc-comments into HTML (a static site), Markdown, and a machine-readable JSON index — the same index the LSP's hover feeds from, so the two never describe an item differently. | Parser/AST |
| **`teko lint`** | Style/best-practice checks beyond type errors, reusing the checker's own structures — the language's law-encoded conventions (no `match` on `bool`, `loop`-only, prefer `[..xs, x]` over a push chain), unused-import and shadowing hints. `--fix` mechanizes the safely-automatable subset. | Checker |
| **`teko repl`** | An interactive read-eval-print session: incrementally evaluate expressions/declarations and inspect values without a full build cycle. | The native -O0 compile-and-run that also backs fast dev iteration |

All four are ordinary `teko` subcommands, implemented as Teko source paired with tests exactly
like every other compiler module — no bespoke plugin architecture, no external process to
install separately.

## A note on `teko repl`'s foundation

`teko repl` evaluates expressions incrementally on top of the native backend's fast, unoptimized
(`-O0`) debug-compile-and-run path (see `self-host-fixpoint.md`). The observable behavior is
incremental, interactive evaluation.
